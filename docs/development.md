# Руководство разработчика

[← На главную](../README.md) · [Архитектура](architecture.md) · [Правила участия](../CONTRIBUTING.md) · [Выпуск версии](releasing.md)

Клиент можно запустить из чистого клона. Для просмотра и разработки интерфейса
не нужны ключ Nimbus API, приватный сервис и настоящие аккаунты TikTok.

**Содержание:** [Окружение](#environment) · [Запуск](#run) ·
[Стенд интерфейса](#mock) · [Проверки](#checks) · [Сборка](#build)

<a id="environment"></a>

## Подготовить окружение

| Компонент | Версия / назначение |
| :--- | :--- |
| Python | **3.14**, сервер клиента и нативное окно. |
| Node.js | **24**, сборка и разработка интерфейса. |
| npm | Зависимости по `web/package-lock.json`, установка через `npm ci`. |
| Windows | Edge WebView2 Runtime для нативного окна. |
| Linux | GTK 3, WebKitGTK 4.1 и PyGObject. |
| macOS | Системный WebKit; приложение собирается отдельно для Intel и Apple Silicon. |

```sh
git clone https://github.com/muted-team/nimbus.git
cd nimbus
```

### Windows · PowerShell

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

### Linux

На Debian/Ubuntu нужны `python3-gi`, `gir1.2-gtk-3.0` и
`gir1.2-webkit2-4.1`; на Arch Linux — `python-gobject`, `gtk3` и
`webkit2gtk-4.1`. Системный PyGObject должен соответствовать версии Python.

Если используете системный PyGObject, дайте виртуальному окружению доступ
к установленным пакетам:

```sh
python -m venv --system-site-packages .venv
source .venv/bin/activate
```

Для разработки только в браузере без нативного окна достаточно обычного
`python -m venv .venv`; GTK и PyGObject в этом режиме не используются.

### macOS

```sh
python -m venv .venv
source .venv/bin/activate
```

### Общие зависимости

В активированном окружении, из корня проекта:

```sh
python -m pip install -r requirements.txt
python -m pip check
cd web
npm ci
cd ..
```

<a id="run"></a>

## Запустить клиент

Соберите интерфейс в `ui/`, затем откройте нативное окно:

```sh
cd web
npm run build:app
cd ..
python app.py
```

`app.py` запускает локальный HTTP-сервер и pywebview. По умолчанию сервер
слушает `127.0.0.1`; сетевой доступ с телефона включается пользователем
отдельно и требует пароля.

Для обычного браузера вместо `app.py`:

```sh
python main.py 8740 127.0.0.1
```

Откройте `http://127.0.0.1:8740`. Браузер использует загрузку файлов;
системный выбор папок доступен в нативном окне.

> **Сборка интерфейса.** `npm run build:app` записывает результат в `ui/`,
> откуда его читает Python. `npm run build` записывает результат в `web/dist/`.
> Если клиент уже используется, собирайте в `web/dist/` или отдельном рабочем
> каталоге, чтобы не менять его интерфейс во время операции.

Обычный сервер работает с локальными данными и может обращаться к сервису.
Для проверки оформления и состояний экранов используйте стенд ниже.

<a id="mock"></a>

## Разрабатывать интерфейс без аккаунтов

В первом терминале, из корня проекта:

```sh
python dev/_ui_mock.py --scenario idle --port 8799
```

Во втором терминале, из `web/`:

```sh
API_TARGET=http://127.0.0.1:8799 npm run dev
```

В PowerShell:

```powershell
$env:API_TARGET = "http://127.0.0.1:8799"
npm run dev
```

Откройте `http://127.0.0.1:5173`. Vite обновляет страницы при изменении кода
и направляет `/api` в стенд. Стенд отвечает вымышленными данными и не выполняет
вход, публикацию или запросы к TikTok.

Состояние можно менять без перезапуска — откройте URL стенда:

| Адрес на `http://127.0.0.1:8799` | Состояние |
| :--- | :--- |
| `/_mock?scenario=idle` | Форма до первого запуска. |
| `/_mock?scenario=running` | Публикация выполняется. |
| `/_mock?scenario=waiting` | Ожидание следующего круга. |
| `/_mock?scenario=done` | Завершённый запуск с отчётом. |
| `/_mock?scenario=restored` | Восстановленный отчёт прошлого запуска. |
| `/_mock?scenario=empty` | Нет аккаунтов, прокси и папок. |
| `/_mock?scenario=clean` | Все аккаунты со входом и без отметок «в тени». |
| `/_mock?scenario=error` | Ошибки загрузки основных списков. |
| `/_mock?auth=1` | Экран пароля, тестовый пароль `1234`. |
| `/_mock?auth=0` | Отключение тестового экрана пароля. |
| `/_mock?proxies=mixed` | Проверенные, недоступные и непроверенные прокси. |
| `/_mock?proxies=empty` | Прокси включены, список пуст. |
| `/_mock?proxies=dead` | Все прокси недоступны. |
| `/_mock?proxies=checking` | Проверка прокси выполняется. |

Неизвестный или пустой сценарий возвращает `400`, не меняя текущее состояние.
Пустой `auth=` ничего не меняет. Смена сценария также сбрасывает состояние
прокси; для отдельных случаев задавайте `proxies` после неё.

Для просмотра готовой сборки стенд умеет отдавать другой каталог:

```sh
python dev/_ui_mock.py --scenario idle --ui web/dist --port 8799
```

Устройство компонентов и правила UI — в [web/README.md](../web/README.md).

## Проверить изменения

Все Python-команды выполняются из корня проекта, в активированном окружении:

```sh
python tools/check_public_tree.py
python tests/run_checks.py
python tests/check_account_parse.py
python tests/check_accounts_bulk.py
python tests/check_config_cache.py
```

Затем проверки интерфейса:

```sh
cd web
npm run typecheck
npm run lint
npx vitest run
npm run build
```

`tests/run_checks.py` запускает `test_*.py` с диагностикой зависаний. Тесты
используют синтетические данные; ключи и реальные аккаунты для них не нужны.
На macOS локальным сетевым тестам нужны доступные loopback-адреса
`127.0.0.2` и `127.0.0.3`; в GitHub Actions они готовятся отдельным шагом.

Проверки на четырёх платформах описаны в [ci.yml](../.github/workflows/ci.yml).
Локальная успешная проверка подтверждает только проверенную систему.

### Изоляция GUI

Предпочитайте headless-браузер. Если нужен X11-сервер для нативного теста,
выберите **явный свободный дисплей ≥99** и проверьте оба пути:
`/tmp/.X<N>-lock` и `/tmp/.X11-unix/X<N>`. Любой существующий путь означает,
что номер занят. Не используйте `Xvfb -displayfd` или автоматический выбор
дисплея.

Задавайте `DISPLAY` и приватный `XAUTHORITY` только команде теста и её детям;
для X11-теста убирайте `WAYLAND_DISPLAY` только у этой команды. Гарантируйте
очистку при завершении и прерывании, останавливайте только собственные PID.
Проверьте, что сокет настоящего рабочего стола не изменился. Если изоляцию
подтвердить нельзя, пропустите GUI-тест и укажите причину.

## Собрать самостоятельное приложение

Собирайте на целевой ОС и архитектуре. В активированном окружении:

```sh
python -m pip install -r requirements-dev.txt
python build.py --dry-run
python build.py
```

Сборщик устанавливает npm-зависимости, собирает `ui/`, запускает Nuitka
и создаёт ZIP в `dist/`. `--dry-run` только печатает команду Nuitka.
`--skip-frontend` использует уже собранный `ui/`.

Проверка содержимого готовых пакетов:

```sh
python tools/check_package.py
```

Для опубликованного выпуска требуются также проверки нативного окна на
каждой платформе — см. [процесс выпуска](releasing.md).
