# Выпуск версии

[← На главную](../README.md) · [Проверки и сборка](development.md#checks) · [История версий](../CHANGELOG.md)

Пользователь получает четыре ZIP-пакета из GitHub Releases. Каждый тег `v*`
запускает сборки на целевых ОС; выпуск публикуется только после успешного
завершения всех сборок и проверок пакетов.

## Что проверяется автоматически

| Платформа | GitHub runner | Окончание имени ZIP |
| :--- | :--- | :--- |
| Windows x64 | `windows-2022` | `win32-AMD64.zip` |
| Linux x64 | `ubuntu-24.04` | `linux-x86_64.zip` |
| macOS · Apple Silicon | `macos-15` | `darwin-arm64.zip` |
| macOS · Intel | `macos-15-intel` | `darwin-x86_64.zip` |

Источники процесса: [ci.yml](../.github/workflows/ci.yml) и
[build.yml](../.github/workflows/build.yml).

## 1. Подготовить изменения

Соберите небольшие проверяемые коммиты. Обновите верхний раздел
`CHANGELOG.md`: версия, дата и короткие изменения, понятные пользователю.
Повышайте версию для выпуска, а не для каждой правки.

Загрузчик `modules/changelog.py` использует этот файл как источник версии
и заметок. Формат заголовков существующих выпусков нужно сохранить.
История закрытых версий остаётся в `0.0.1`–`0.0.9`.

## 2. Проверить кандидат

Выполните [Python- и frontend-проверки](development.md#checks), затем
убедитесь, что CI проверил **тот же коммит** на четырёх платформах.
Проверьте дерево на пользовательские данные и приватные файлы.

Для локальной сборки на целевой системе:

```sh
python -m pip install -r requirements-dev.txt
python build.py --dry-run
python build.py
python tools/check_package.py
```

Используйте чистый рабочий каталог сборки. `build.py` откажется перезаписывать
существующий результат Nuitka. Не собирайте поверх используемого экземпляра.

## 3. Поставить тег на проверенный коммит

Тег должен совпадать с верхней версией `CHANGELOG.md`: например, для записи
`1.0.1` используется `v1.0.1`. Пример для заранее выбранной следующей версии:

```sh
git tag v1.0.1 <проверенный-коммит>
git push origin v1.0.1
```

Отправка тега запускает публикацию: это отдельное действие сопровождающего.
Не передвигайте уже опубликованные теги. Ручной запуск `workflow_dispatch`
собирает артефакты для проверки, но без тега выпуск не создаётся.

## 4. Дождаться проверки готовых программ

Workflow сборки устанавливает Python 3.14 и Node.js 24, запускает проверки,
собирает интерфейс и самостоятельное приложение, затем открывает нативное
окно пакета и проверяет основные разделы.

Для Windows используется `tools/smoke_windows.mjs`; для Linux и macOS —
`tools/smoke_native.py`. Проверки выполняются на синтетических данных.
Снимки и отчёты сохраняются в артефактах `smoke-<платформа>`; при ошибке
упаковки также сохраняется `diagnostic-<платформа>`.

## 5. Проверить опубликованный выпуск

После успешных четырёх сборок release-job собирает архивы, извлекает
пользовательские заметки из `CHANGELOG.md` и создаёт GitHub Release.

Перед объявлением проверьте:

- Тег указывает на нужный проверенный коммит.
- Выпуск действительно появился в [Releases](https://github.com/muted-team/nimbus/releases).
- В нём есть все четыре ZIP, соответствующие версии и архитектурам.
- Название и заметки совпадают с подготовленной версией.
- Нативные отчёты успешны, архивы содержат нужные лицензии.

Наличие записи в changelog, тега или архива CI само по себе не подтверждает,
что выпуск опубликован. При ошибке исправьте причину и проверьте результат
workflow до объявления готовности.
